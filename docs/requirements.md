## 1. プロジェクトの概要

Mirage は、AI と音声で自然に会話でき、カメラなどを利用したインタラクションにも対応する AI アシスタントアプリ。

単に AI と会話できるデモを作るのではなく、今あるアプリを発展させて、実用性・拡張性・信頼性を備えた本格的なシステムにしていく。

**プロジェクトの基本方針**

- 既存の Mirage をベースに改善する。ゼロから作り直すことを前提にしない。
- 3D 表現に過度な工数を使わず、AI・バックエンド・システム設計に注力する。
- 動作するだけでなく、長期運用・性能・障害対応まで考慮した設計にする。
- 将来の拡張を考えつつ、最初から不要な複雑さを持ち込まない。

## 3. 機能要件

### 3-1. 3D から 2D へ変更

- 現在の 3D 表現を 2D キャラクター中心の UI に変更する（D-002 / P10）。
- キャラクターモデルやアニメーションを一から作り込むことには、あまり工数を使わない。
- 既存技術やライブラリを活用し、キャラクターの表示や視覚的な反応を実現する。
- 開発リソースは、見た目の作り込みよりも AI やシステムの技術面に割く。

### 3-2. AI との対話体験

- 音声による自然な会話を継続する。
- 会話中の割り込みなど、リアルタイム対話で重要な挙動を改善する。
- 今後の追加要件に応じて、AI の処理や会話管理を拡張できる構成にする。

### 3-3. 長期記憶

AI が会話内容を一時的に扱うだけでなく、必要な情報を継続的に保存・参照できる仕組みを導入する（P12 → P13）。

検討対象となる要素:

- 会話やユーザー情報の永続保存
- 過去の情報の検索・取得
- 古い情報や矛盾した情報の更新
- 不要な記憶の削除
- 記憶を使った応答の改善

記憶の保存方式や、どの情報を記憶するかという具体的なルールは §10 の実装要件で決める。


## 4. 技術構成の方針

今までの話では、次の構成が有力（確定ではない。D-003 を参照）。

| レイヤ | 構成 |
| --- | --- |
| フロントエンド | React + TypeScript（2D キャラクター・UI・カメラ・マイク・音声の入出力） |
| API・通信 | バックエンド（Go） |
| バックエンド | Go（API・会話管理・AI 処理の調整・長期記憶・障害対応） |
| データベース | PostgreSQL（会話履歴・長期記憶・セッション情報などの永続化） |

**React・Next.js・Go の使い分け**

- React + TypeScript: 既存のフロントエンドを継続利用する。
- Go: バックエンドを強化するための導入候補。並行処理、API 設計、エラー処理、運用などを学びながら実装する。
- PostgreSQL: 長期記憶など、永続化が必要なデータの保存先候補。
- Next.js: 現時点では必須ではない。管理画面や公開 Web サイトなど、必要性が明確になった段階で検討する（D-008）。

重要: 既存の React アプリを、技術選定だけを理由に Next.js へ移行する必要はない。また、カメラ制御などブラウザ側で動く機能を、無理に Go へ移すこともしない。


## 5. 非機能要件（品質・信頼性）

「一応動く」だけでなく、実際に使い続けられるシステムにする。

**エラー処理・障害対応**

- 外部 API や AI サービスが失敗した際の適切な処理
- タイムアウト、リトライ、キャンセルの設計
- フォールバック処理と、正常復帰後の再開
- 重複処理や古い応答による不整合の防止

**パフォーマンス**

- 音声対話の応答速度
- カメラ処理や画面描画の負荷
- メモリ使用量や CPU 負荷
- 同時処理時の安定性
- 改善前後の数値による比較

**テスト**

- ユニットテスト
- API やデータベースの統合テスト
- 実機カメラがなくても動かせるテスト
- 外部 API の障害を想定したテスト
- 負荷テスト・長時間稼働テスト

**運用・監視**

- 構造化ログ
- エラーや遅延の監視
- 障害原因を追跡できる仕組み
- CI/CD によるテスト・ビルド・デプロイの自動化
- バックアップや復旧手順の整備


## 6. 既存コードの改善方針

特にカメラ関連は、現在も動いている機能なので、全面的な書き換えから始めない。まず既存コードを調査し、必要な部分から段階的に改善する。

- カメラの起動・停止・デバイス管理
- 外部 API との通信
- 検出処理とフォールバック制御
- 座標や距離などの計算
- React の UI や状態管理
- テストしやすいロジックと、ブラウザ依存の処理の分離
- カメラのストリーム、タイマー、イベントリスナーなどの確実な解放

これらの責務を整理し、障害が起きたときに原因を特定しやすい構造を目指す。


## 7. 開発方針

- 既存資産を活用し、必要な部分から改善する。
- 最初からマイクロサービスなどに分割しすぎない。
- 長期的な拡張性と、現在の開発効率のバランスを取る。
- 技術を導入すること自体を目的にせず、必要性に基づいて選定する。
- 性能や信頼性は、感覚だけでなくテストと計測結果で評価する。
- 設計上の判断と、その理由をドキュメントに残す（→ `decisions.md`）。
- **テストは機能実装と同時に入れる**（D-006）。P14 の完成を待つな。


## 8. ポートフォリオとしての目標

大学在学中の開発経験を、将来のエンジニア就職や起業にも活用できる成果物にしたい。

単なる機能紹介ではなく、次のような技術的な成果を示せることを目指す。

- 全体アーキテクチャと設計意図
- API 設計・データベース設計
- テストと品質保証
- 障害への対応や復旧設計
- パフォーマンスの測定結果
- CI/CD と運用の仕組み
- 技術選定の理由とトレードオフ

目標は、AI を組み込んだアプリを作ったという実績だけでなく、設計・実装・テスト・運用まで考えられるエンジニアだと示せるプロジェクトにすること。

### P13 長期記憶

**やること**: 記憶の保存・検索・更新・削除・矛盾解決。**先に下記を実装前に決める**（決めるまでは「未確定」に残す）。

| 論点 | 決めること（例） |
| --- | --- |
| 何を記憶するか | 機械的に判定できる事実だけ（名前・好み・前回の用件など）。自然な文章の長期記憶は本リポ外（D-009） |
| いつ作成・更新するか | 会話終了時＋明示的な事実抽出。会話中の逐次追記はしない |
| 矛盾の解決 | 新しい日時を優先。更新時刻と出典（セッション ID）を持つ |
| 検索方法 | ユーザー ID ＋ タグ/キーの完全一致。ベクトル検索は本フェーズスコープ外 |
| 削除済み記憶の残留防止 | 論理削除（`deleted_at`）＋ 検索・文脈注入の両方で除外 |
| 完了の判定 | 下記の完了条件がすべて通る |

**完了条件**

- [ ] 記憶がセッション単位ではなくユーザー/来場者単位で保持される
- [ ] 同じ項目の新しい情報が古い情報を上書きする
- [ ] 矛盾ケース（新しい方優先）のテストがある
- [ ] 削除した記憶が検索結果にも文脈注入にも出ない
- [ ] 記憶が 0 件でも文脈注入が壊れず会話が成立する
- [ ] 記憶を使った応答が、記憶なしの場合と答えが変わる（回答に記憶が反映されている）
