## 1. プロジェクトの概要

Mirage は、AI と音声で自然に会話でき、カメラなどを利用したインタラクションにも対応する AI アシスタントアプリ。

単に AI と会話できるデモを作るのではなく、今あるアプリを発展させて、実用性・拡張性・信頼性を備えた本格的なシステムにしていく。

**プロジェクトの基本方針**

- 既存の Mirage をベースに改善する。ゼロから作り直すことを前提にしない。
- 3D 表現に過度な工数を使わず、AI・信頼性・システム設計に注力する。
- 動作するだけでなく、長期運用・性能・障害対応まで考慮した設計にする。
- 将来の拡張を考えつつ、最初から不要な複雑さを持ち込まない。

**今回のスコープ（2026-10-29 再定義）**

- 北極星（大きく）: 置いておくだけで、その場の人が困りごとを解決できる案内エージェント。
- 今回の完成形（狭く深く）: 1施設・1端末・複数人検知・会話は1人ずつ・日本語/英語。`接近 → 第一声 → 用件 → 映像文脈 → 回答 → 見送り → ログ` の1本＋管理画面（認証・状態・セッション・設定）。
- 深さ: 落ちても縮退して続く／計測できる／テストと CI で守られている。指標は解決率・完遂率、p95 応答遅延、30分連続稼働、複数人来場時の破綻率。
- 今回やらない: AIの長期記憶・来場者をまたぐ記憶・来場者アカウント、1端末で同時に複数人会話、複数端末の一元管理、3D/実素材の作り込み、マイクロサービス・24/7（D-012 / D-013）。

## 3. 機能要件

### 3-1. 3D から 2D へ変更

- 現在の 3D 表現を 2D キャラクター中心の UI に変更する（D-002 / P10）。
- キャラクターモデルやアニメーションを一から作り込むことには、あまり工数を使わない。
- 既存技術やライブラリを活用し、キャラクターの表示や視覚的な反応を実現する。
- 開発リソースは、見た目の作り込みよりも AI やシステムの技術面に割く。

### 3-2. AI との対話体験

- 音声による自然な会話を継続する。
- 会話中の割り込みなど、リアルタイム対話で重要な挙動を改善する。
- 今後の追加要件に応じて、AI の処理や会話管理を拡張できる構成にする。

### 3-3. 記憶（2026-10-29 にスコープ外）

AIの長期記憶・来場者をまたぐ記憶・再訪時の呼び戻しは行わない（D-012）。会話の文脈は Gemini Live のセッション内だけで扱う。会話ログは管理・調査用に Studio の DB へ保存してよいが、次の会話の文脈には注入しない（D-014）。

### 3-4. 複数人同時対応

- 1台のカメラで複数人を検知・追跡し、管理画面に全員を表示する（D-015）。
- 会話は同時に1人だけ。近い・正面・未対応の人を優先し、会話中の人は離脱するまで切り替えない。
- 離脱後は次の人へ。順番待ちの案内は今回の必須にしない。
- 同時に複数人会話はしない（音声の混線を避ける）。

### 3-5. 多言語（日本語＋英語）

- 来場者の発話言語を自動判定し、同じ言語で返答する（D-016）。
- 最初の声・プロンプト・TTS を日英で用意する。管理画面は日本語のみ。
- フォールバック経路はかな/漢字 vs ラテンの簡易判定で `lang` を切り替える。

### 3-6. 管理画面・認証

- Studio に管理者1ロールのログインを置く（D-014）。
- Dashboard（Mirageの状態・検知中の来場者・アクティブ・待ち・言語）、Session List/Detail（会話ログ・イベント）、Settings（言語・閾値・表示）を最小構成とする。
- 未認証の管理画面をネットワークに公開しない。Mirage→Studio はデバイストークンで認証する。
- 管理画面は日本語のみ。

### 3-7. リアルタイムWeb検索（P21 / P22）

- 施設の外の最新情報（天気・営業時間・イベント・ニュース）を聞かれたら、Web で調べて答える（D-017）。
- 検索は Gemini Live の function calling から呼ぶ。**必要時のみ**（自分が知らない・鮮度が要る）実行し、毎ターンは呼ばない。
- 回答には出典（サイト名と URL）を含める。取得できなかった場合は、推測で埋めずに「今は調べられない」と伝える。
- 検索サービスの実行場所は Studio の API Route。ブラウザは Studio だけを叩く。
- 検索の抜粋に具体的な値（気温・営業時間など）が無い場合は、本文取得（crawl4ai）まで進む。抜粋だけで「分からない」と答えない。
- ツール実行中は無音にせず、フィラーか「調べています」の短い一言で間を埋める。
- 検索結果は短時間（5分程度）キャッシュし、同じ質問の連打で外部を叩かない。
- 天気は構造化API（Open-Meteo）を優先し、検索しない。数値は検索の抜粋に入らないことが多い（D-019）。
- 施設の営業時間・場所・料金は `src/data/facility.ts` を正とし、検索しない。書いていないことは推測しない。
- APIキーは `studio/.env` に置き、ブラウザには Live 用の短命トークンだけ渡す（D-018）。
- フォールバック経路（Ollama）は今回の対象外。検索は Gemini Live 経路のみ。


## 4. 技術構成の方針

技術構成は次のとおり（2026-10-29 に D-012 / D-014 で確定）。

| レイヤ | 構成 |
| --- | --- |
| Mirage 本体 | React + TypeScript（Vite）。カメラ・マイク・2Dキャラ・Gemini Live |
| 管理画面 | Next.js App Router（`studio/`）。Dashboard / Sessions / Settings |
| 管理 API | Studio の Next.js API Routes（Go は不採用。D-012） |
| DB | SQLite（運用データのみ）。複数端末・リモート時に PostgreSQL（D-014） |
| 通信 | Mirage → Studio: WebSocket（状態/イベント）＋ REST（セッション/設定）。Mirage ↔ Gemini/Groq は直結 |
| 認証 | 管理者1ロール（署名付き Cookie）＋ Mirage 用デバイストークン |
| 検索・取得 | 検索: Tavily（外部API、キーは Studio）。代替: `ddgs` API（:4479、開発用）。天気: Open-Meteo。本文: crawl4ai 0.9.5（:11235、`scripts/crawl-server.py` 経由）。ローカル系は localhost のみ（D-017 / D-019） |

**React・Next.js・Go の使い分け**

- React + TypeScript: Mirage 本体。カメラ・マイク・描画・会話はブラウザに置く。
- Next.js: `studio/` の管理画面と管理 API。DB・認証・運用データを担当する（D-014）。
- Go: 2026-10-29 に不採用（D-012）。PostgreSQL は複数端末・リモート運用が必要になったら検討する（D-014）。

重要: 既存の React アプリを、技術選定だけを理由に Next.js へ移行する必要はない。カメラ制御などブラウザ側で動く機能はブラウザに置く。

**分離の原則**: Studio が落ちても Mirage は案内を続ける。Mirage は Studio への送信失敗で会話を止めない。

**秘密情報**: Gemini の API キーはブラウザに露出する（`VITE_GEMINI_API_KEY`）。ローカル展示前提とし、公開する場合は制限付きキー＋quota で運用する（D-012）。`.env` はコミットしない。


## 5. 非機能要件（品質・信頼性）

「一応動く」だけでなく、実際に使い続けられるシステムにする。

**エラー処理・障害対応**

- 外部 API や AI サービスが失敗した際の適切な処理
- タイムアウト、リトライ、キャンセルの設計
- フォールバック処理と、正常復帰後の再開
- 重複処理や古い応答による不整合の防止
- Studio（管理API/DB）が落ちても Mirage が案内を継続する

**パフォーマンス**

- 音声対話の応答速度
- カメラ処理や画面描画の負荷
- メモリ使用量や CPU 負荷
- 複数人来場時の安定性（検知・アクティブ選択・離脱）
- 改善前後の数値による比較

**テスト**

- ユニットテスト
- 外部 API（Gemini / Groq / Ollama）をモックした統合テスト
- Studio の API/DB（セッション保存・取得）の統合テスト
- 実機カメラ・マイクがなくても動かせるテスト
- 外部 API の障害を想定したテスト
- 認証（未ログイン拒否・デバイストークン）のテスト
- 負荷テスト・長時間稼働テスト

**運用・監視**

- 構造化ログ
- エラーや遅延の監視
- 障害原因を追跡できる仕組み
- CI/CD によるテスト・ビルドの自動化
- 設定（`.env`）と依存サービスの復旧手順の整備
- 会話ログの保存期間と削除手順


## 6. 既存コードの改善方針

特にカメラ関連は、現在も動いている機能なので、全面的な書き換えから始めない。まず既存コードを調査し、必要な部分から段階的に改善する。

- カメラの起動・停止・デバイス管理
- 外部 API との通信
- 検出処理とフォールバック制御
- 座標や距離などの計算
- React の UI や状態管理
- テストしやすいロジックと、ブラウザ依存の処理の分離
- カメラのストリーム、タイマー、イベントリスナーなどの確実な解放

これらの責務を整理し、障害が起きたときに原因を特定しやすい構造を目指す。


## 7. 開発方針

- 既存資産を活用し、必要な部分から改善する。
- 最初からマイクロサービスなどに分割しすぎない。
- 長期的な拡張性と、現在の開発効率のバランスを取る。
- 技術を導入すること自体を目的にせず、必要性に基づいて選定する。
- 性能や信頼性は、感覚だけでなくテストと計測結果で評価する。
- 設計上の判断と、その理由をドキュメントに残す（→ `decisions.md`）。
- **テストは機能実装と同時に入れる**（D-006）。P14 の完成を待つな。
