## ★ 今後の方針（2026-07-23）— 実装一段落、磨き＋見せる形へ

機能はもう十分乗った。開発の重心が「演出の微調整」ループに入っており、エンジニアリング評価の伸びしろとしては飽和ぎみ。今後は新規機能より、以下3方向で「完成度・作りの質・見せ方」を上げる。**評価者は企業と教授**（研究/学会は狙わない。既存の使えるものはガンガン使い、選定・統合・堅牢性・判断を厚くするのがエンジニアリングの勝ち筋）。

### 開発環境: Mac → Windows へ移行
- 理由: 今後は新規実装よりブラッシュアップ主体。GPU機/TripoSG環境がWindows(WSL2)側にあるため集約したい
- 移行チェックリスト:
  - git clone、Node/npm（`npm install`）
  - AivisSpeech の Windows版インストール（TTS、port 10101）
  - Ollama Windows版（LLMフォールバック、port 11434）
  - Python venv + `stt_server.py`（ローカルSTTフォールバック、port 8000）
  - **`start-fallback.sh`はbash前提 → Windows用の`.ps1`/`.bat`を用意するか、WSL2で実行**
  - Groq APIキー等の`.env`移行
- ※フロント(vite)自体はOS非依存。詰まるのは補助サービスの起動系のみ

### 1. 堅牢性（「たまたま動く」→「保証できる」）
- **起動の一発化**: 今は手動で4サービス(vite/Aivis/STT/Ollama)を立ち上げている。Windows向けにワンスクリプト（PowerShell）＋各ポートのヘルスチェック＋落ちたら自動再接続に。→「なぜ自動化したか」を実体験でブログ/面接で語れる
- **障害時の自己回復**: Groq障害→ローカル(Ollama/whisper)へ明示的に切替、STT失敗時の挙動明確化。NEXTで繰り返し積み残しの「Groqレート制限・会場Wi-Fi・フォールバック実地確認」をここで潰す
- **長時間安定**: 30分連続稼働でメモリリーク・音の詰まり・TTSキュー詰まりが出ないか検証

### 2. 設計・コード品質（「作り」として評価される）
- **`Avatar.tsx`(1130行)の分割**: 典型的な神コンポーネント化。呼び込み〜会話の状態遷移(far/mid/near × convState × noticing/beckoning/glance)を明示的なステートマシンに切り出す →「複雑な状態をどう設計したか」を面接で語れる最高のネタ
- 移動/演出/表情/会話をモジュール分割、ハードコード閾値を設定に集約

### 3. 見せる・説明できる形（評価者に届ける）

## ★ ガチ版mirage 設計思想（本気で企業/プロ品質にするなら、2026-07-23の壁打ち集約）

### 大方針: 道A = 技術コアを本番水準に1点突破
1人開発でプロ品質を狙うなら、全部をプロダクト化せず「リアルタイム対話AI統合システム」という技術の核を企業の本番コード水準に磨く。研究でも事業でもなく、エンジニアリングで殴る。
- 別の道B（用途を1つに絞って事業化）は、デザイン/営業/運用が要り1人だと限界。将来構想としてのみ保持
- 今のmirageは「作者が横にいて1台で動かす展示デモ」。プロダクトは「作者不在で24/7、誰の課題を解くか定義され、落ちても自明に復旧する」もの。差は機能量でなく**土台**

### ユースケース: 呼び込みからの会話（＝技術優先順位を決める起点）
mirageの芯は **呼び込み(能動的な入口) × 会話(双方向) × 一期一会**。集客サイネージは呼び込むだけ(一方通行)、受付AIは会話だけ(受動)。両方を繋ぐのがmirageの唯一無二のポジション。
- 活きる場所: 能動的な集客/呼び込みが価値になる所（商業施設・イベント・店頭の客引き・展示ブースの人寄せ）
- 活きない場所: じっくり相談・正確な事務手続き・継続的な顧客関係（能動性が邪魔／一期一会前提の設計と合わない）

このユースケースが技術優先順位を規定する（今後ブレたときの判断基準）:
```
ユースケース: 呼び込みからの会話（能動入口 × 双方向対話、一期一会）
       ↓ が要求する
最優先: 会話フェーズの騒音耐性（指向性マイク / VAD / 複数人ターゲット選択）
        ※呼び込んで足を止めさせても、騒音下で会話が破綻したら全部台無し = 出口が壊れてたら意味がない
土台:   アーキ分離 → その上にストリーミング / バージイン
差別化: 能動呼び込み × オフアクシスの視覚インパクト
一期一会ゆえ: 短時間で満足させる（すぐ覚える・褒める・テンポ）= 既存の強みで方向は合っている
```

### 存在を成立させる構造（感覚を増やすより"繋げて生きてる感"を作るのが本質）
```
入力: 耳(STT) 目(MediaPipe) 触覚 + パラ言語(声色)
中枢: 気分エンジン(内面状態) ← 全機能をここ経由で滲ませる = "心"
出力: 口(TTS) 体(モーション) 表示(オフアクシス投影)
文脈: 時間性(生活リズム) + 場の空気(社会性)
```

### 機能選定の基準（重要 — これで映えの追加に逃げるのを防ぐ）
「映えるか」で選ばない。**本質的に体験を上げるか × 技術的に難しいか × 企業に語れるか** の3点で選ぶ。
- ❌ 却下: 演出の微調整の延長（チラ見頻度・独り言・小物追加）= 飽和・価値薄
- ✅ 採用: 対話AIとして本質的に効く、技術的歯ごたえのある機能

### 本質機能候補
- **対話**: バージイン(割り込み発話) / E2Eストリーミング低レイテンシ（頭から喋る＝"間"を消す）
- **知覚(MediaPipe)**: 視線推定(目が合う) / 表情認識 / ジェスチャー認識(手を振る→振り返す) / 注意モデル高度化(誰に話すか)
- **表現**: 頭トラッキング×オフアクシス投影（覗く角度で実在感＝擬似ホログラフィックディスプレイ）/ 正確なeye contact / シェーダー質
- **中枢**: 気分エンジン（機嫌/退屈/エネルギーの内部状態→表情・声・動きに滲む。バラバラの反応を一貫した人格に束ねる。"生きてる感"のコスパ最高）
- **文脈**: 時間性(時刻/経過で状態変化・既存の窓時刻同期を波及) / パラ言語(声色で感情を聞く＝傾聴キャラ直結)

二枚看板: **バージイン（対話）** と **頭トラッキング×オフアクシス（表現）**。

### 実装順序（土台が先、その上に本質機能）
```
Phase 1: アーキ分離（フロント/バックエンド、STT→LLM→TTSのオーケストレーションをサーバーへ、鍵を隠す）← 地面
Phase 2: E2Eストリーミング + バージイン（体験の核、一番効く）
Phase 3: 気分エンジン / 永続記憶 / 頭トラッキング×オフアクシス / 視線・表情
並行:    テスト / CI / 監視 / パフォーマンス設計(MediaPipe重処理はWebWorkerで分散)
```
※今の単一クライアント構造のままだと上記の高度機能は綺麗に乗らない。土台は「機能を乗せる地面」

### 制約として認識すべき点（＝設計判断として語れる = エンジニアリング）
- 頭トラッキング型オフアクシスは**1視点しか作れない** → 複数人が覗くと破綻。「1人が正面で体験するモード」or 代表視点で近似
- MediaPipe重処理 × レンダリング同時 = フレームレート低下 → 処理分散設計が必要

### 想定外リクエストへの対処（例: 展示で「踊って」と無茶振り 2026-07-23）
対話AIの品質は「できないこと」をいかに自然にさばくかで差が出る（graceful degradation）。身体アクション系の無茶振り（踊って/ジャンプ/回って/○○のポーズ）は無限で全部にモーションは用意できない。段階的対処:
1. **即席**: Mixamoからダンス等を1個リターゲットして仕込む（既存のwalk/wave/drink/warrior idleと同じ手順で足せる）。頻出無茶振りに先回りで備える
2. **会話フォールバック**: SYSTEM_PROMPTに「できないリクエストは可愛くかわす」を仕込み、モーションが無くても会話で優雅に対応
3. **ガチ版**: 有限モーションプール + LLMがリクエスト→モーション選択（意味理解でマッピング）+ カバー外は会話フォールバック
4. **将来の本解決**: text-to-motion（＝上の「検討中」で保留したものが、ここで意味を持つ。動きで完全に応える最終形）
- **運用ループ**: 展示で実際に来た無茶振りは貴重な実データ。記録して頻出パターンに対処を用意していく（データドリブン改善）

### 実運用の具体課題（音声・カメラ）— 研究でなく既存技術で解くエンジニアリング
展示の実環境で顕在化した課題。新アルゴリズムは作らず、既存ライブラリ/ハードの選定・統合・チューニングで解く。
- **線引き**: 研究=新VAD/話者分離手法を"発明" / エンジニアリング=既存を自環境で動かす。やるのは後者。堂々とやってよい

**音声**
- ① 不特定多数の声を拾う → 目の前の1人に絞る:
  - 音量ゲート(RMS閾値)で遠くの雑音を無視
  - **指向性マイク(ハードで解く)** = 展示で一番効く。ソフトで頑張る前にハードで解くのが賢い判断。今すぐ買って試せる(土台と無関係)
  - ビームフォーミング/声紋識別は展示には過剰なことが多い
- ② 喋り終わっても認識が続く(endpointing):
  - **Silero VAD**で発話区間を正確に切る＋無音区切り閾値の調整。今の`no_speech_prob`は認識結果の"後処理"、VADは"そもそも録るか"の前処理でこっちが根本的

**カメラ**
- ① 複数人でカクカク(パフォーマンス): MediaPipe処理を**WebWorker**へ逃がす／検出頻度を下げる（＝土台のパフォーマンス設計）
- ② 向きが定まらない(ターゲット選択のブレ): **ヒステリシス**(一度選んだ人を乗り換えにくく)＋スムージング。既存の`faceSize`平滑化の発想をターゲット選択にも展開。=「注意モデル高度化」

**着手順**: 指向性マイクは今すぐ試せる。ソフト側(VAD/WebWorker化)はアーキ分離後の方が綺麗に入る。位置づけは道AのPhase3(知覚の高度化)＋堅牢性

## ★ 検討中: text-to-motion（結論保留、2026-07-23 本人アイデア）

テキスト→3Dモーション生成をやりたい。所感:
- **メリット**: 面白い＆映える。今は手続き型＋Mixamoリターゲットで動きが固定。状況に応じてLLMが動きを生成できれば表現の幅が段違い、技術デモのインパクトも大
- **懸念**:
  1. 「ブラッシュアップ」ではなく重い新規実装。研究寄り(MDM/MotionGPT/T2M-GPT系)で、本人が興味ないと言った研究領域に片足入る
  2. 生成が重く遅い→AITuberの即応性(命)と本質的に相性が悪い。会話のテンポが死ぬ
  3. 出力(SMPL/HumanML3D)→VRM humanoidリターゲットが必要。Mixamoで苦労したのと同種の沼をプログラム的にやることになる(TripoSGの二の舞リスク)
- **現実的な落とし所**: リアルタイム生成は展示のレイテンシ要件と衝突。やるなら**オフライン生成→VRMA化して既存ジェスチャープールに足す**限定運用
- **位置づけ**: 磨きフェーズを一区切りした後の「次の山」として切り離すなら賛成。今の磨きと並行は両方中途半端になるリスク

## ★ 状況（2026-07-19実機検証まとめ）

07-17までの新機能を初めて実機（マイク・カメラ・実際に人を動かして）で検証。以下が判明・修正済み。

1. **Whisper STTを`whisper-large-v3-turbo`→`whisper-large-v3`に変更**（体感速度・精度とも向上）
   Groq公式ベンチマークだと、Groqの専用ハードウェア上ではturboの方が速いとは限らず
   （v3無印299倍速 vs turbo216倍速というGroq自身の計測もある）、WERはv3無印8.4%/turbo12%と
   無印の方が明確に精度が高い。速度低下の心配がほぼ無いまま精度だけ上がったので変更。

2. **チラ見(胸ひねり込み)を実機確認 → 意図通り**
   Playgroundで背中を向けて歩いている最中にチラ見を発火させ、肩越しに振り返ってすぐ戻る
   動きを目視確認。真後ろ向きでも胸のひねりのおかげで振り返れている。

3. **`far`ゾーンの呼び込み仕様を再確認・一部誤って壊しかけたので復元**
   実機で「farに入ると4秒で勝手に喋る」のを見て「チラ見だけの想定では？」という疑問が出て、
   一度farを完全無音にしてみたが、それは行き過ぎだった（「呼び込み」自体がこの展示のAフェーズの
   核であり、無くすと遠くの通行人に一切アピールできなくなる）。最終的に**元の仕様のまま**で確定:
   - `far`: 普段は無音、4秒粘ると初回呼び込み、以降は4秒間隔で呼び込みを繰り返す

## 2026-07-16: 気づいた瞬間に振り向いてくれないバグを調査・修正・検証

本人から「不在で歩いてる最中に後ろを向いていたら、気づいた瞬間の驚き・手招みはするのに来場者側を向いてくれない（＝背中を向けたまま驚いて手を振る）」と報告（スクショ2枚付き）。

**本命の原因（＝これが実際の症状の直接原因。ブラウザ実機で確認済み）**:
`Avatar.tsx`の移動分岐で、会話中(`conversing`)は`paused`と同じ枝に入れて**位置も向きもまとめて固定**していた。この`conversing`ガードは元々「会話中に距離ゾーンがmid/near間を行き来して勝手に歩き出す/後ずさりするのを防ぐ」ため位置を止める目的だったが、体の向き(`bodyYaw`→`scene.rotation.y`)まで巻き込んで固定していた。徘徊で後ろを向いた瞬間に「不在→near」で一気に来場者が現れると、①気づき演出(驚き＋手招き)が発火するのとほぼ同時に②App側が`zone==="near"`で`startConversation()`→`conversing=true`になり、③次フレームでAvatarが`conversing`枝に入って**向きが固定**→背中を向けたまま。しかも驚き表情(`noticing`ゲート)・手招みの腕(`beckoning`ゲート)は別セクションなので**そのまま再生される**。結果「背中を向けて驚いて手を振る」状態に。修正: `paused`と`conversing`を別の枝に分け、`conversing`中も体の向きだけは常に来場者(正面=yaw0)へ`bodyYaw`をlerpし続ける（位置は従来通り止める）。

**副次の修正（フレームレート堅牢化。単独では上記の主因は直らない）**:
気づき演出の振り向き(`NOTICE_TURN_LERP`)・視線/首ロック(`NOTICE_GAZE_LERP`)がdelta非依存の「1フレームあたり一定割合」lerpだった。TTS合成/MediaPipe処理でフレームレートが落ちると2秒の演出時間内に必要フレーム数を稼げず回転しきれない懸念があったため、`damp(rate60, delta)=1-(1-rate60)^(delta*60)`ヘルパーで実時間収束に変換（気づき演出の3箇所と会話中の振り向きに適用）。

**検証（claude-in-chromeで実ブラウザ駆動）**: Playgroundに「会話中フラグ(擬似)」トグルを新設（`fakeConversing`。実マイク/LLMなしで`conversing`状態だけAvatarへ渡す）。不在で徘徊させ**完全に背中を向けた静止状態**を作ってからトグルON→その場で約180°回転して正面(カメラ=来場者側)を向き、位置は動かず固定、を確認（中央へ瞬間移動する初回の紛らわしい挙動は、待ち時間中に徘徊が勝手に正面化した交絡と判明したので、静止背面から素早くONにして交絡を排除して再確認）。GIF `turn-to-visitor-fix.gif` に記録。型チェックも通過。**残: 実カメラ＋実会話(TTS同時実行)下での最終確認**（Playgroundの擬似フラグでの確認までは完了）。[[feedback_visual_verification]]

## 2026-07-14: 通しリハーサルで見つかった3件を修正（顔サイズ検知のバタつき／Whisperの「はい」ハルシネーション／⏸停止ボタン無反応）

本人が実際に動かして気づいた不具合3件を修正。

**1. 顔の向きを変えると急に歩き出す**
`useFaceDetection.ts`の`faceSizeRef`（距離ゾーン判定の元になる顔の横幅）が、MediaPipeの生のバウンディングボックス幅をそのまま毎フレーム代入していただけで平滑化していなかった。首を振る等ちょっとした頭の向き変化だけで幅が瞬間的に縮み、`getDistanceZone`の閾値をまたいでゾーンが行き来し、キャラが急に歩く/後ずさりする原因になっていた。指数移動平均(`FACE_SIZE_SMOOTHING=0.35`)で軽くならして解消（初回検出時は0からゆっくり立ち上がると誤判定するため、値が0の時だけ即座にスナップする特別扱いあり）

**2. Whisperが無音なのに「はい」と幻聴する**
`WHISPER_HALLUCINATION_PATTERNS`は「ご視聴ありがとうございました」等の定型文だけを狙い撃ちしており、「はい」「うん」等の短い相槌は本物の発話でも起こりうるため意図的に対象外にしていた。今回、GroqのWhisper APIリクエストに`response_format=verbose_json`を追加し、返ってくる`segments[].no_speech_prob`（Whisper自身が判定する「無音らしさ」スコア）が閾値(0.6)以上の場合だけ結果を破棄するように変更。単語のブラックリストと違い、本物の短い相槌は通しつつ無音/環境音由来の幻聴だけを弾ける。ローカルSTTフォールバック(`stt_server.py`)はno_speech_probを返さないためこの判定の対象外（本人の要望により「ありがとうございました」単体（「ご視聴」なし）の誤爆は今回は未対応のまま）

**3. デバッグの「⏸ 停止」ボタンが押しても何も変わらない**
`paused`状態は呼び込みセリフ・視線を外した時の反応・会話自動開始などのトリガー系だけをガードしており、`Avatar.tsx`側の歩行・接近/徘徊ロジックは`paused`を一切認識していなかった（Avatarに渡してすらいなかった）ため、停止ボタンを押してもキャラは普通に動き続けていた。`Avatar`に`paused`propを追加し、trueの間は移動処理を丸ごとスキップしてその場に固まるように変更。あわせて、停止ボタン押下時に会話中なら`stopConversation()`も呼ぶように、HUDの「稼働中/停止中」表示も`paused`を反映するように修正（今までは`started`だけを見ていて、一時停止中でも「稼働中」と表示されていた）

3件ともPlaywrightで実際に確認済み（型チェックも通過）。

## 2026-07-14: 不在→検知時の「瞬間移動っぽい」動きを修正

本人から「不在から人を検知した時、遠い/中距離/近いへの遷移がワープしてるみたいで不自然」と報告。

**原因**: `Avatar.tsx`の来場者検知時の分岐（`zone !== "absent"`側）は、位置を`lerp(position, target, 0.05)`で直接補間していただけで、(1) 移動方向にかかわらず常に正面(yaw=0)を向かせていた（徘徊で横や後ろを向いていても検知した瞬間に正面向きへ）、(2) 移動速度が徘徊時の`WANDER_SPEED`(0.35m/s)と無関係で、距離が大きいと初速が数m/s相当になり得た（`lerp`のalpha0.05は距離に比例した速度になるため）。この2つが組み合わさり、徘徊中の位置から検知時に「体の向きと違う方向へ速いスピードで滑る」ように見えていた。歩行アニメーション自体は正しく再生されていたが、移動の向き・速さが合っていなかったため不自然に見えていた

**対応**: 目標位置までの距離が0.05を超える間（`returningFromWander`）は、徘徊時と全く同じロジック（`WANDER_SPEED`で速度上限をかけた移動＋実際の移動方向を向くyaw）を使うように統一。目標付近まで来たら、従来通りの緩やかなlerpで正面を向かせる（覗き込み演出用の小さな前後移動はそのまま）

**確認**: Playwrightで`playground.html`を開き、不在のまま数秒待ってキャラを徘徊させた後「近い」ボタンをクリックし、遷移中を連写（100ms〜3.2s後まで）。以前のような無方向の滑りではなく、向きを変えてから歩いて中央へ戻る動きになっていることを確認。型チェックも通過

**気づいたが今回は未対応**: 中央付近で静止した状態が背中向き（カメラにお尻を向ける格好）に見えるコマがあった。これはこの修正で新たに発生したものではなく、以前のスクリーンショットでも同様の向きで映っていたため、既存の仕様（もしくは別の既知の癖）の可能性が高い。気になるようなら別途調査

### 座るアニメーション【✅完了・2026-07-09 → ❌2026-07-12に撤去】

Mixamo「Sitting Idle」→ Blender MCPでVRoidモデルにリターゲット → `public/avatar/sit.vrma`として書き出し → `Avatar.tsx`に統合。`room.glb`の椅子(`Chair_Seat`)に実際に歩いて座り、しばらくして立って徘徊に戻る行動をAI無しで自律実装した。

**Mixamoの取得はPlaywrightでブラウザ操作**（ヘッドありChromiumを起動しCDP経由で接続、ユーザーがログインだけ手動→検索・ダウンロード設定はこちらで自動操作）。Mixamoログインは対話操作が必要なため、ダウンロードだけ自分でやってもらう運用より、実際にブラウザを見せながら進める方がスムーズだった。

**リターゲット手順**
1. Mixamoから`X Bot@Sitting Idle.fbx`をダウンロード（Format: FBX Binary, Skin: With Skin, FPS: 30。座りモーションは元々その場に留まるため歩行と違いIn Placeオプション自体が出ない）
2. `tools/walk_retarget.blend`（歩行と同じファイル）にVRoidモデル＋座りFBXを読み込み
3. 腰・脚・背骨(spine/chest/upperChest)はWorld空間、**腕は今回リターゲットしない**（後述の理由でMixamoの腕モーションは使わず手続き型に切り替え）
4. 全ボーンで`nla.bake`（`only_selected=False`。選択ボーンだけだと`bpy.context.selected_pose_bones`が0件になりベイクが空振りするBlender 5.1.2の挙動を確認、`channel_types`未指定だと「ベイクする物がありません」で無言失敗する点にも注意）
5. `export_scene.vrma`で書き出し

**踏んだ落とし穴と直し方**
- **足首が180°逆を向くバグ（再発）**: 歩行の時と同じ「Mixamo→VRMの座標変換に起因」のバグ。今回はBlenderの`matrix_world`でMixamo・VRM双方の足ボーンのレスト姿勢をワールド空間で数値比較し、X軸が正確に反転していることを確認してから補正（World空間でY軸180°回転を後乗算）。目視だけで補正方向を決めると何度も逆に転がる（Local空間に変えたら悪化、補正方向を間違えて二重に壊れる、を繰り返した）ので、**感覚ではなく実際の回転行列を比較して補正量を決めるべき**という教訓
- **腕はMixamoモーションを使わず手続き型に変更**: 「Sitting Idle」クリップは前髪や髪を触るような手のジェスチャーが入っており不自然だった。Blender側で腕ボーンを外す（コンストレイント削除＋identityで再ベイク）→`Avatar.tsx`側で`isSitting`時に腕だけ固定ポーズを直接代入（後述のバグにより`lerp`では効かない）
- **`lerp`で腕を制御すると全く動かないバグ**: `createVRMAnimationClip`が対象にするのは`Normalized_*`という正規化ボーン（`vrm.humanoid.getNormalizedBoneNode`と同一オブジェクト）で、sitMixerが毎フレームこのボーンをidentityへ強制的に書き戻す。`lerp(現在値, 目標値, 係数)`で基準にしていた「現在値」がその都度identityへリセットされるため、何フレーム経っても目標に近づかない（6%ずつ0から動いて0に戻るだけ）。**Mixerが触るボーンを手続き型で上書きする時はlerpではなく直接代入（`rotation.set(...)`）でないと蓄積しない**
- **腕の回転軸が直感と違い調整に苦戦**: Z軸=T-poseから体側に下ろす動き、X軸=前後の振り、という基本は合っていたが、Euler回転順序(XYZ)の影響でXとZの値が独立に効かず、値を変えるたびに大きく姿勢が変わって収束しづらかった。最終的に「前に出す」調整は不安定なため断念し、**直立時と同じ`z=1.2, x=0.1`（体の横に自然に下ろす）に近い値へ落ち着けた**
- **座高が高すぎる**: MixamoとVRoid、双方の想定する椅子の高さが違うため、Hipsのワールド位置をそのまま使うと座面から浮く。`SIT_Y_OFFSET`（`Avatar.tsx`）でsitWeightに応じて沈める簡易対応
- **徘徊・着席移動中に机や椅子を貫通する**: 直進移動のみで障害物回避がなかったため。`avoidObstacles()`で近づいたら押し返す簡易ステアリングを追加。椅子へ向かう時は椅子自体を回避対象から除外（そこへ行きたいので）、机だけ避ける

**行動AI（コードのみ、LLM不要）**
`Avatar.tsx`に`chairState`（`roam`/`toChair`/`sitting`）を追加。徘徊の一時停止のたびに35%の確率で椅子へ向かい、着いたら6〜14秒座って起立→徘徊再開。来場者を検知したら（座っていても）中断して立ち上がりつつ中央へ戻る、という流れは徘徊→接近の既存の重みブレンド機構にそのまま乗せられた。

**残課題**
- 障害物回避は簡易的な反発ベースで経路探索はしていないため、配置によっては貫通が残る可能性

**新規バグ: 座ってから立った直後、一瞬腕が変な方向に伸びる【✅修正・2026-07-10】**
本人が実機で発見。「座ってて立った直後」のスクリーンショットで片腕が横に伸びきって見える不具合。
- 原因1: 肩(shoulder)ボーンが`isSitting`分岐でしかリセットされておらず、「発話中」「歩行中」「それ以外」の
  各分岐では一切触られていなかった。一度座ると、その後ずっと肩だけ座り姿勢の角度に固定されたままになる
  実害のあるバグ（`Avatar.tsx`の該当3分岐すべてに肩リセットを追加して解消）
- 原因2（本命、Playwright+実際の回転値ログで特定）: three.jsの`AnimationMixer`は`effectiveWeight`が低い間、
  クリップの値と「バインド時点の元の姿勢」を重みで按分するが、その「元の姿勢」が期待していた
  基本姿勢（腕を下ろした状態）ではなくT-pose寄りの値になっていた。座り→歩行に遷移した直後は
  `walkWeight`が0から立ち上がる途中のため、腕が一瞬T-poseに近い水平位置まで伸びて見えていた
  （`console.log`で実際の`rArm.rotation`を5Hzで記録し、`walkWeight`と連動して値が変化する様子を確認して特定）
- 対策(第1弾): `isWalking`分岐にlerpベースの補正(`standPull`)を追加したが、本人から
  「座ってなくても、そもそも歩き始めの最初は毎回こうなる」と報告あり。実際に**一度も座らせず
  ページ読み込み直後の初回徘徊**をPlaywrightで連写して再現でき、座り→歩行に限らず
  **「isWalking が false→true に切り替わる瞬間全般」で起きる不具合**と判明。lerpによる緩和だけでは
  低fps環境や初回フレームで収束が間に合わないケースがあった
- 対策(第2弾): `walkWeight < 0.25`の間は基本姿勢へ`.rotation.set()`で直接スナップし、
  閾値を超えたらlerpベースの`standPull`に切り替える二段構えに変更。Playwrightで(a)ページ読み込み直後の
  初回徘徊、(b)座る→立つ、両方を連写して改善を確認。歩行中の自然な腕振り自体は妨げていない
  （`walkWeight`が十分上がった後はスナップが発動しないため）
- 本人から「やっぱり座って立った直後に同じバグがある」と再報告。第2弾修正だけでは不十分と判明し、
  さらに2つの原因を追加で特定・修正:
  - `autoSitting`が`chairState`より1フレーム遅れてfalseになるタイミングバグ。`sitDuration`超過時、
    `chairState.current = "roam"`は即座に切り替わるが`autoSitting.current`をその場でfalseにしていなかったため、
    次フレーム冒頭の`isSitting`計算（`autoSitting`参照）が古い値を読み、`chairState`はもう`"roam"`なのに
    `isSitting`だけ1フレーム遅れてtrueのまま残っていた（腕が座り姿勢のまま固定される一因）。
    `sitDuration`超過の分岐内で`autoSitting.current = false`を即時実行するよう修正
  - `isSitting`がtrue→falseに切り替わった"その瞬間"を`wasSittingForArms`refで検知し、腕・肘・肩を
    基本姿勢へ`.rotation.set()`で強制ハードリセットする保険を追加（`walkWeight`のタイミング依存の
    補正だけでは環境によって収束が間に合わないケースへの対策）
  - Playwrightで座る→立つを50ms間隔で連写（計16フレーム、立ち上がりからwalkWeightが
    ほぼ1になるまでの全過程をカバー）して再検証し、腕の伸び・破綻が一切発生しないことを確認。
    以前のデバッグログ（`console.log`によるフレームごとの`rArm.rotation`記録）は分岐処理が走る**前**の
    中間値を記録していたため、実際は正しく補正された最終値と食い違って見えていた点も判明
    （ログの設置位置が誤っていただけで、`standPull`修正自体は機能していた）

### 行動タグ（LLMが動きを選ぶ）システム【最小版✅完了・2026-07-08、伸び追加✅2026-07-10】
Blenderを使わずコードだけで完結する範囲でまず実装。「歩く/手を振る/頷く/腕組み/何もしない」の構想のうち、
`[nod]`（頷く）・`[tilt]`（首をかしげる）の2つを手続き型（neckボーンの一時回転）で実装。

- `useConversation.ts`: LLM応答ストリームの冒頭で`^\[(nod|tilt)\]`を検出・除去（`ACTION_TAG_RE`）。見つからなければ最大10文字待って諦める。検出したら`actionRef`に`{tag, id}`をセット、`id`はトリガーの度に増分（Avatar側は値の変化でなくid変化を見て新規トリガーと判定）
- `SYSTEM_PROMPT`にタグの使い方を一言追記（「絵文字・記号禁止」ルールの例外として明記しないとLLMが使ってくれないので注意）
- `Avatar.tsx`: `actionRef`のid変化を検知して0.7秒の単発モーション再生。**"head"ボーンはVRMのLookAt(視線追従)が毎フレーム上書きするため使えず、代わりに"neck"ボーンを使う**（three-vrm-coreのソースを`grep`し、LookAtが触るのは"headBone"のみと確認済み）
- `tilt`は左右どちらに傾げるかをトリガーの度に`Math.random()`でランダム決定（最初は右固定だったが偏りがあるとの指摘で修正）
- Playground.tsxに手動トリガーボタンを追加して動作確認（Playwright+スクリーンショットで頷き・首かしげ双方向の動きを目視確認済み）
- 残り（歩く/手を振る/腕組み等）は歩行同様Blenderでのリターゲットが必要なため、座るアニメーション等と合わせて後日

**バグ1: ジェスチャーが全く見えない**

**バグ2（根本原因）: `scene.frame_end`不一致でクリップが壊れる**

5. Text-to-Motionは「全部をAI生成」にしない
ここが今回の重要な結論。
最初から、
「踊って」→ 毎回AIが完全なダンスモーションを生成

にする必要はない。
むしろ、
Level 1：Motion Command
歩く
止まる
座る
手を振る
踊る
ジャンプ
見る
などの既存モーションをAIが選択。
Level 2：Motion Blending
複数の動きを組み合わせる。
例えば、
「歩きながらこっちに手を振って」

なら、
下半身 → walk
上半身 → wave
頭 → look_at_user
のようにする。
これだけでもかなり「AIが身体を持っている」感じが出る。
Level 3：Text-to-Motion
その上で、
「ロボットみたいに踊って」
「もっと激しく踊って」
「恥ずかしそうに踊って」

など、既存モーションでは対応できない部分だけAI生成にする。
これが現状一番現実的。
