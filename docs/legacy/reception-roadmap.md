## 着手順

```
[今]  P21 検索・取得基盤（Studio API ＋ Tavily/ddgs ＋ crawl4ai ＋ Open-Meteo）
        └ 「必要時に調べて答える」を、UI 抜きで curl から通す
[次]  P22 Live からのツール呼び出し（天気・検索・本文・施設情報）
        └ ここが今回の核。応答を止めずに調べる動線を通す
[次]  P23 検索品質・遅延の計測（P6 と統合）
[次]  P17 Studio 管理基盤（契約・SQLite・管理者認証・デバイストークン）
[次]  P18 Studio 管理画面（Dashboard / Sessions / Settings）
[次]  P19 複数人（検知は複数・会話は1人ずつ）
[次]  P20 多言語（JA/EN 自動判定）
[並行] P14 テスト / P15 CI・監視（各機能にテスト同行。D-006）
[終]  P16 通し品質（複数人・JA/EN・検索あり・Studio停止時・30分・解決率・p95）
[任意] P7 第一声 / P8 感情タグ / P10 実素材
```

理由:

- **検索を先に**: 「その場の困りごとを解決する」の核は、知らないことをその場で調べられること。ここが弱いまま管理画面を作っても、中身のない運用画面になる（D-017）。
- **基盤 → ツール呼び出しの順**: 検索と本文取得を API として先に固定し、curl で通してから Live に配線する。UI と外部依存を同時にデバッグしない。
- **Studio は後退、ただし API の置き場としては先に使う**: 管理画面・認証・運用DBは P17/P18 に残すが、検索の中継先として `studio/` の API Route は前倒しで使う（D-014 / D-017）。
- **複数人は「検知は複数・会話は1人ずつ」**: 1台のマイク/スピーカーで同時会話すると混線する。検知と会話を分ければ、複数人来場時も品質を測れる（D-015）。
- **多言語は JA/EN 自動判定**: 来場者に言語切替UIを触らせない。フォールバックの言語判定だけ簡易ヒューリスティックにする（D-016）。
- **AIの記憶とGoは戻さない**: 管理用の会話ログは保存するが、次の会話の文脈には注入しない（D-012 / D-014）。検索は記憶ではなく、その場の取得。
- **P14/P15 を後回しにしない**: 機能ごとにテストを付ける。P16 でまとめて測る（D-006）。
- **P7/P8/P10 は任意**: 体験の向上には効くが、品質保証の完了条件には含めない（D-013）。

## 候補・条件付き

- **複数端末の一元管理**: 1端末で品質が通った後に検討する。DB を PostgreSQL へ移すタイミングと合わせる。
- **表情×会話の紐付け計測**: P16 の解決率・p95 と一緒に、表情と会話の対応をログから見る。P16 の完了条件には含めない。
