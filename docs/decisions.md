## D-014 管理・認証・運用データは Studio（Next.js）に集約する

- **決定**: 管理画面・認証・運用データの保存は `studio/`（Next.js App Router）が担当する。Mirage 本体は状態・イベントを WebSocket、セッション/設定を REST で Studio に送る。DB はまず SQLite（ファイル）、複数端末・リモート運用が必要になったら PostgreSQL へ移す。認証は管理者1ロール（環境変数＋署名付き HttpOnly Cookie）。Mirage→Studio は管理セッションとは別のデバイストークンで認証する。
- **理由**: Studio は既に管理画面の土台がある（dashboard/sessions/settings）。Go を足さずに API・DB・認証を学べる。SQLite はローカル展示で運用が軽く、ORM を差し替えれば PostgreSQL に移れる。
- **不採用案**:
  - (a) Go + PostgreSQL を別途立てる → サービスが増え、今回の1端末規模に対して過剰。
  - (b) 認証なしで LAN 公開 → 管理画面から設定・ログが見えるため危険。
  - (c) 最初から PostgreSQL + Docker → 環境構築が先に立ち、画面と品質保証が遅れる。
- **保存するもの**: セッション、インタラクションイベント、設定、管理者（または環境変数の管理者）、会話ログ（運用記録）。
- **保存しないもの**: AI の長期記憶・来場者をまたぐ記憶。会話ログは管理・調査用で、次の会話の文脈には注入しない。顔画像・顔特徴量は保存しない。
- **リスク**: 会話ログに個人情報が入り得る。保存期間を決め、管理画面から削除できるようにする。デバイストークンは Mirage のブラウザに埋め込まれるため、LAN 内の展示端末前提とし、公衆網に晒さない。


## D-015 複数人同時対応は「検知は複数・会話は1人ずつ」

> DJ 本線では未使用（D-023）。観客の人数・表情を Director の入力に使うとき、検知部分だけ再利用する。

- **決定**: 1台のカメラで複数人を検知・追跡し、管理画面には全員を表示する。会話は同時に1人だけ。近い・正面・未対応の人を優先して選び、会話中の人は離脱するまで切り替えない。離脱後は次の人へ。順番待ちの案内は今回の必須にしない。
- **理由**: 1台のマイク/スピーカーで同時会話すると音声が混線する。検知と会話を分ければ、複数人来場時も破綻せず、品質を測れる。
- **不採用案**: 同時に複数人会話（話者分離・複数マイクが必要）、複数端末の一元管理（今回は1端末）。
- **影響**: アクティブ来場者の選択を純関数にし、ブラウザ無しでテストする。管理画面に「検知中/アクティブ/待ち」を出す。P16 で「来場者が連続で入れ替わっても破綻しない」を測る。

## D-017 リアルタイムWeb検索は Studio API 経由（ddgs ＋ crawl4ai）

> DJ 本線では未使用（D-023）。Studio の API 中継・短命トークンの土台として残す。DJ の MC から検索させるかは未決。

- **決定**: 施設外の最新情報（天気・営業時間・イベント・ニュース）が必要な質問は Web 検索で解決する。実行場所は **Studio の API Route**（`studio/app/api/web/`）に置き、ブラウザや Mirage から外部サービスを直接叩かない。検索は **`ddgs` APIサーバ**（`:4479`）、必要なときだけ **crawl4ai**（`:11235` の `/md`）で本文 Markdown を取る。Gemini Live の function calling でモデルが必要時のみ呼び、出典付きで答える。スニペットで足りる場合は本文取得をしない。
- **理由**:
  - DuckDuckGo の HTML エンドポイント直叩きは 2026-10-31 時点で HTTP 202 のボット判定ページが返り、結果 0 件（実測）。`ddgs` は duckduckgo/bing/brave 等を横断し、片方が 429 でも逃げられる。
  - ブラウザ直結は CORS で不可なうえ、トークンと SSRF の踏み台をクライアントに置くことになる。Studio は既にサーバなので新しいサービスを増やさずに済む。
  - crawl4ai は JS 描画込みで LLM 向け Markdown を返し、LLM キー不要（`/md`）。Docker を入れずに済むよう、公式サーバと同じ `POST /md` の形を `scripts/crawl-server.py`（FastAPI 約50行）で再現した。公式 Docker に移しても Studio 側は変えなくてよい。
- **不採用案**:
  - (a) ブラウザから DuckDuckGo HTML を fetch して正規表現パース → CORS とボット判定で不可。
  - (b) Google CSE / Brave Search API → キーと課金が増える。今回は ddgs で足りる。
  - (c) crawl4ai の `/llm`・`/extract` で要約までさせる → LLM が二重になり遅く高い。本文 Markdown だけ取り、判断は Gemini がする。
  - (d) 常に全文取得 → 遅い。スニペット優先、不足時のみ取得。
- **影響**: P21（基盤）→ P22（Live からの呼び出し）→ P23（品質・遅延の計測）。検索失敗時は「今は調べられない」と正直に返して縮退する。`ddgs` と crawl4ai は**バージョン固定**（上流変更で壊れやすい）。両サービスは localhost のみに束縛する（crawl4ai は `127.0.0.1:11235`、http(s) 以外と private/loopback URL は拒否）。P17 で認証を入れたら検索 API も配下に置く（現状は LAN 内の誰でも叩ける）。


## D-018 秘密は Studio に集約し、Live は短命トークンで接続する

- **決定**: APIキー（`GEMINI_API_KEY` / `TAVILY_API_KEY`）はすべて `studio/.env` に置く。ブラウザは Live 接続時に Studio の `POST /api/live/token` から**短命トークン**（`v1beta/auth_tokens`、`uses: 1`・30分）を受け取り、それを SDK の `apiKey` として使う。vision の見た目コメントも `POST /api/vision/comment` に移す。ルートの `.env` からは秘密を消す。
- **理由**:
  - ブラウザのバンドルからキーを消せる。漏れても30分・1セッションで失効する。
  - Studio で WebSocket を中継する案は、音声が1ホップ増えて遅くなるので採らない。短命トークンなら音声はブラウザ↔Google 直結のまま。
  - 検索・天気・vision がすでに Studio 経由なので、「秘密の置き場所」を1か所にできる。
- **不採用案**:
  - (a) Studio で Live の WebSocket を中継 → 遅延と実装量が増える。
  - (b) `VITE_GEMINI_API_KEY` のブラウザ直結を続ける → バンドルにキーが残る（D-012 の割り切りを extend しない）。
  - (c) ephemeral token に `liveConnectConstraints` でシステムプロンプトまで固定 → プロンプト変更のたびにトークン発行が要る。まずはトークンのみ。
- **影響**: Studio が**会話の必須依存**になる（今までは検索だけ）。`pnpm dev` が Studio も起動するので運用は変わらない。ephemeral token は preview 機能で `v1beta` のみ。失敗時は「Studio 未起動」と明示エラーにする（黙って諦めない）。30分を超える会話はトークン切れで再接続が必要。


## D-019 「自前で持つ」データを3層に分ける（施設情報 / 天気API / 検索）

> DJ 本線では未使用（D-023）。`src/data/facility.ts` と Studio の検索 API は残しているが、DJ のプロンプトには接続していない。

- **決定**: 回答の材料を役割で分ける。
  1. **施設情報**（営業時間・場所・料金・設備）… `src/data/facility.ts` に持ち、システムプロンプトへ注入して**検索せず即答**。書いていないことは推測せず「スタッフに確認してください」と言う。
  2. **天気** … Open-Meteo（キー不要・無料）を Studio の `/api/web/weather` から取得し、**10分キャッシュ**。Gemini のツールは `get_weather`（`web_search` を使わせない）。
  3. **それ以外の最新情報**（店・イベント・ニュース）… **Tavily**。`TAVILY_API_KEY` が無ければ `ddgs` にフォールバック（開発用）。
- **理由**:
  - 実測（2026-11-03）で「明日の神奈川の天気」は検索こそ当たるが、抜粋が宣伝文だけで数値が無い。**検索エンジンを増やしても直らない**（同じ3サイトが返るだけ）。ページを読むか、構造化APIを使うのが正解。
  - Tavily は `results[].content` に約500字の本文チャンクを返すので、ddgs の「抜粋だけ」問題が起きにくい。1検索=1クレジット、無料1,000/月。
  - Google CSE は **2027-01-01 に終了**（新規受付も停止）。将来性がないので採用しない。
  - ddgs は各エンジンの結果ページを直接叩くため規約上グレーで、個別backendは実測で全滅（`auto` のみ）。無制限でもない。開発用のフォールバックに格下げする。
- **不採用案**:
  - (a) Brave / Google / Tavily を**並列に混ぜる** → 同じ結果を3倍のコストと遅延で買うことになる。順位統合のコードも要る。
  - (b) SearXNG 自前 → Docker 前提（この環境は Docker 無し）。規約上のグレーさも解消しない。
  - (c) 埋め込みRAG → 施設情報は数十項目なのでプロンプトで足りる。
- **影響**: `get_weather` を追加（遅延 約200ms、キャッシュ時 0ms）。`web_search` は Tavily の本文チャンクを返すため `fetch_page` の出番が減る。crawl4ai はフォールバックとして残す。展示後は `scripts/top-questions.mjs` で検索された質問を集計し、施設情報へ移す。


## D-020 表情のライブ監視は「Mirageが撮ってStudioが最新1枚を表示」にする

- **決定**: 表情はブラウザの MediaPipe FaceLandmarker の blendshape で smile / surprised / confused を出す。Mirage が 100ms ごと（約10fps）に「160pxのJPEG1枚＋スコア＋顔矩形＋距離＋yaw」を Studio の `/api/vision/live` へ POST し、Studio は**メモリ上の最新1件だけ**を保持して **SSE（`/api/vision/live/stream`）で即時プッシュ**する。`/vision` は受け取った瞬間にカメラ＋検出枠＋スコアを描画する。**画像は保存しない**（上書きのみ）。
- **理由**: 表情の抽出はすでに Mirage 側の MediaPipe で動いている。Studio に別のカメラ／推論を二重に持たせず、展示端末が見ているものをそのまま確認できる。WebSocket / WebRTC はこの確認用途（低fps）には過剰。
- **不採用案**: (a) Studio が自前でカメラを開く → 別端末では展示のカメラが見えない。(b) 映像を WebRTC で流す → 実装量に見合わない。(c) 画像を保存して再生 → プライバシーと容量の理由で不採用。
- **影響**: Studio が落ちていても Mirage は止まらない（送信失敗は無視）。ライブ表示は開発・運用確認用で、会話の必須依存にはしない。会話文脈へは開始時に1回＋会話中は表情が安定して変わったときだけ（1.5秒安定・最短10秒・同じ表情は1回）追注入する。


## D-021 カメラ監視の映像は WebRTC（P2P）、顔枠・表情は SSE

- **決定**: Studio `/vision` のカメラ映像は、Mirage → Studio の **WebRTC（P2P）** で流す。SDP の交換だけを Studio の HTTP メールボックス（`/api/vision/rtc/offer|answer`）で行い、映像はブラウザ同士で直接送る。顔枠・表情スコアは従来どおり SSE（`/api/vision/live/stream`、約10fps）で送り、WebRTC が繋がるまでの間は 160px JPEG をフォールバック表示する。
- **理由**: 10fps の JPEG 連投では「確認用の鏡」としては粗い。WebRTC なら 30fps・低遅延で、MediaStream をそのまま送れる（再エンコード不要）。Next.js の Route Handler に WebSocket サーバーは無いので、接続時だけ HTTP で offer/answer を交換する方式にした（STUN/TURN 無し・同一マシン/LAN 前提）。
- **不採用案**: (a) LiveKit / mediasoup を立てる → 1視聴者の確認用途には過剰。(b) WebSocket シグナリング → Next.js に別サーバーが要る。(c) JPEG の fps を上げる → 帯域と CPU が増える割に滑らかにならない。
- **制限**: 認証なし・TURN なし（NAT越え不可）・送信は1台・最後に開いた `/vision` が優先。外部公開や多視聴者は LiveKit + TURN に置き換える。`shortcut: 同一マシン/LAN 前提の HTTP シグナリング, 遠隔・多視聴者が必要になったら LiveKit + TURN へ`
- **影響**: Studio が落ちても Mirage は止まらない（送信失敗は無視）。WebRTC が失敗しても JPEG フォールバックで監視は継続する。


## D-022 AI DJは「LLMディレクター＋身体エンジン」で作る（2026-11-08 本線化）

> 2026-11-08 更新: D-023 で AI DJ を本線に切り替えた。以下の「並行スパイク」「レセプション本線」は決定当時の記録。

- **決定**: レセプション本線（`/`）は残したまま、`dance.html` に **AI DJ / 3Dパフォーマー** のスパイクを並行開発する。LLMは60fpsの関節生成器ではなく、1〜2小節ごとに発話・選曲・停止・歩行・ダンスを決める**ディレクター**とする。身体は **Locomotion / Dance / Gesture / Face** の層に分け、まずはクリップ＋プロシージャル（拍同期のbounce/sway/head nod）で動かす。モーションの90%はatom＋procedural、10%だけ将来の生成モデルに差し替える。MCはGemini Liveの出力専用セッション（`capture:false`）で動かし、音楽をダッキングする。LLMの出力はモデル非依存の `ShowAction` とし、`MotionSource` の裏で生成モデルを交換できるようにする。
- **理由**:
  - 「LLMが考えてリアルタイムで踊る」を、LLMに毎フレーム関節を出させる方法で実装すると、レイテンシと破綻が展示に耐えない。
  - クリップ＋プロシージャルなら即時・安定・安い。生成モデルはサビの特別枠に限定すれば、遅延・失敗時も公演が止まらない。
  - MCを出力専用にすると、スピーカーの音楽をマイクが拾うハウリング問題を初期スパイクから外せる。観客入力はカメラ／表情の再利用資産から後で合流させる。
- **不採用案**:
  - (a) LLMが直接60fpsの関節を生成 → レイテンシ・安定性・コストで不可。
  - (b) 完成した振付を複数持ってLLMが選ぶだけ → 「考えて踊る」にならない。
  - (c) 最初から生成モデル（TM2D / FlowerDance / EDGE）を本線にする → コード・ライセンス・GPU・リターゲットが未検証。まずソケットを切る。
  - (d) MCをマイク入力込みで開始 → 音楽の回り込みで誤反応する。まず出力専用で間合いとダッキングを固める。
- **影響**: `src/dance/` / `src/hooks/useGeminiLive.ts` のカスタムプロンプト・ツール・`capture`・`prompt()`。`docs/ai-dj-architecture.md` が本線の設計。`requirements.md` / `roadmap.md` は D-023 で AI DJ 本線に更新済み。`shortcut: MCは8小節ごとのテキストプロンプトで判断, 観客・カメラ入力とnextBar量子化が入ったら再設計`
